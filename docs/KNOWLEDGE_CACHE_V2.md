# Collective Knowledge Cache v2 — signed content-addressed shards

**Status: development only. Not a released or enabled client contract.**

## Producer and authority

The initial v2 publisher derives its data **only** from the already-reviewed v1
snapshot generated by `cache/records_intake.py` on trusted `main`. It does
not grant new evidence authority or allow LLM-proposed records to be published
automatically. The existing v1 endpoint and signatures continue to be produced.
The v2 format is a distribution layout, not evidence that a migration works.

```text
main-reviewed history.json + knowledge.json
  -> records_intake.py (pinned public fixtures, registry/version checks)
  -> v1/cache.json (validated source)
  -> shards_v2.py (deterministic partition, digest + size limits)
  -> v2/index.json + v2/shards/<prefix>/<sha256>.json
  -> protected cache-signing job (domain-separated Ed25519 index.sig)
  -> GitHub Pages
```

Client trust: pin the publisher's Ed25519 public key, verify
`b"DepLoom public migration records v2\\x00" + SHA256(exact index bytes)`,
reject revision rollback or equal-revision replacement, and verify *every*
fetched shard's exact digest/size and closed schema before use. Shard paths are
relative, content-addressed and must never be interpreted as commands or URLs.
An incomplete edition must not become active. On failure retain the last
verified edition or bundled v1 examples; never treat a cache hit as independent
project acceptance.

The v2 index remains bounded at 2 MB; a single JSON shard at 256 KB. The
package-name SHA256 first-byte prefix distributes records into 256 buckets.
This supports deterministic chunking within a bucket without a single 2 MB
global records limit. Publishing a v2-native curated record corpus (beyond
the current v1 allowlist) needs a *separate reviewed admission gate* with
independent source evidence before it can be enabled.

No project manifests, lockfiles, proprietary dependencies, telemetry, prompts
or untrusted contributor scripts are uploaded. The builder reads data only;
it never checks out or runs a contributor's tree.

## Standalone smoke (from the repository root)

With a Python 3.12+ environment containing the pinned consumer contract:

```sh
PYTHONPATH=build/contracts/src python cache/records_intake.py "$(git rev-parse HEAD)" /tmp/cache.json
PYTHONPATH=build/contracts/src python cache/shards_v2.py /tmp/cache.json /tmp/knowledge-v2
PYTHONPATH=build/contracts/src python -m unittest discover -s cache -p 'test_shards_v2.py' -v
```

The protected publishing workflow signs the exact generated index. Do not
generate a production signing key in a contributor runner.
